# docs/PR

PR을 올릴 때마다 그 PR의 구체적인 설명과 관련 문서를 담는 공간이다. **PR 하나에 폴더 하나**를 쓴다.

## 이름 규칙

- 폴더: `MMDD_PR{번호 3자리}_{작업-이름}/`
  - `MMDD`는 PR을 **처음 연 날**로 고정한다(나중에 바꾸지 않는다).
  - 번호는 GitHub PR 번호. 3자리로 맞추고 모자라면 앞을 0으로 채운다. 1000번부터는 그대로 쓴다.
  - `{작업-이름}`은 브랜치의 작업 이름과 맞춘다(예: 브랜치 `feat/diary-feed` → `diary-feed`).
- PR 설명서: 폴더와 같은 이름의 `.md` (예: `1106_PR003_diary-feed/1106_PR003_diary-feed.md`)
- 추가 문서: 같은 접두를 쓴다(예: `1106_PR003_diary-feed_api-sample.md`).
- 리뷰 기록: `MMDD_PR{번호 3자리}-REVIEW_{작업-이름}.md`

## 원칙

- **PR 설명서가 없는 PR은 존재해서는 안 된다.** 경미한 변경도 간소 양식의 설명서를 둔다.
- PR 설명서가 정본이다. GitHub PR 본문은 [.github/pull_request_template.md](../../.github/pull_request_template.md) 양식으로 요약과 설명서 경로만 담는다. 둘이 다르면 설명서가 맞는 것으로 보고 본문을 고친다.
- 양식 선택
  - **일반 양식**: 경미하지 않은 변경
  - **간소 양식**: 경미한 변경, 릴리스 PR (`release: vX.Y.Z (YYYY-MM-DD)`)
  - **리뷰 기록**: 선택. 병합 전에 실제로 리뷰했고 지적 사항이 있을 때만 쓴다. 리뷰어가 없거나 지적 사항이 없으면 쓰지 않는다.

## 절차

1. 작업 브랜치의 첫 커밋을 푸시하고 Draft PR을 열어 번호를 받는다.
2. 곧바로 그 번호로 PR 폴더와 설명서를 만들어 같은 브랜치에 커밋·푸시한다. 작업 설계 문서가 있으면 관련 PR 칸도 번호로 채운다.
3. GitHub PR 본문에 설명서 경로를 넣는다.
4. 작업이 끝나면 설명서의 변경 사항·테스트 절을 갱신해 따로 커밋한다.
5. Ready for review 전 확인
   - [ ] 설명서가 브랜치에 커밋되어 있다
   - [ ] 설명서의 링크·브랜치·작업 설계 경로가 실제와 같다
   - [ ] PR 본문에 설명서 경로가 있다
   - [ ] 작업 설계가 있다면 진행 기록이 갱신됐다
   - [ ] 커밋이 작게 나뉘어 있다
   - [ ] 테스트 데이터가 바뀌었다면 report 문서가 갱신됐다

## 일반 양식

```markdown
# PR{번호} {PR 제목}

- 작성일: YYYY-MM-DD
- 작성자:
- 브랜치: `{작업 브랜치}` → `dev`
- PR 링크:
- 관련 이슈:
- 관련 설계: (docs/design의 문서·절, 결정 번호)
- 작업 설계: (docs/work/... 경로)

## 목적

## 변경 사항

| 구분 | 파일/모듈 | 내용 |
|---|---|---|

## 설계·결정 반영

(따른 설계와 결정. 설계와 다르게 한 부분이 있으면 그 내용과 이유. 진행 중 가정한 내용도 한 줄씩)

## 디자인 영향

## 테스트

(실제로 돌린 검사와 결과, 생략한 검사와 이유.
테스트 데이터나 테스트 계정이 바뀌었으면 report 문서를 갱신했는지 한 줄로)

## 리뷰어가 볼 곳

## 배포·마이그레이션 메모

## 관련 문서
```

## 간소 양식

경미한 변경과 릴리스 PR에 쓴다.

```markdown
# PR{번호} {PR 제목}

- 작성일: YYYY-MM-DD
- 작성자:
- 브랜치: `{브랜치}` → `{대상 브랜치}`
- PR 링크:

## 목적

## 변경 사항

## 테스트
```

## 리뷰 기록 양식

```markdown
# PR{번호} 리뷰 기록

- 리뷰일: YYYY-MM-DD
- 리뷰어:
- 확인한 범위: (커밋, 파일, 검사)

## 수정할 사항

| # | 심각도 | 위치 | 내용 | 처리 | 상태 |
|---|---|---|---|---|---|

(처리: 이 PR / 리뷰 수정 PR / 보류. 병합을 막는 문제만 이 PR에서 고치고,
나머지는 이후 리뷰 수정 PR에서 고친 뒤 상태 열을 갱신한다)

## 검사 기록

(원격 CI가 돌지 않았다면 로컬에서 돌린 검사와 생략한 검사)
```
